Fleet works with any coding agent that can edit local files and run terminal commands. No Fleet-specific plugin, account, or hosted assistant is required.

## Give your agent the contract

Before creating an app, point your agent at `fleet agent` — it prints Fleet's app model (every app is a directory registered in place via `fleet init`), authorized commands, and workflow. You can also install it as a global `SKILL.md` for coding agents with:

```sh
fleet agent --install
```

Inside an existing app folder, point your agent at the generated `AGENTS.md`. A good first prompt looks like:

> Read AGENTS.md. Add a search bar to this notes app. Keep the existing data format, use Fleet queries and mutations, and check `fleet logs notes` after editing. Do not start a separate dev server.

Your agent edits `client/index.tsx`, `client/style.css`, and `server/index.ts`. Fleet takes care of bundling, reloading browsers, HTTPS, and sign-in.

## Inspect before editing

Your agent can check the live state of an app at any time:

```sh
fleet list --json
fleet inspect notes
fleet logs notes
```

- `fleet list --json` lists every registered app and its build status in machine-readable JSON.
- `fleet inspect notes` shows the current build revision, exported queries/mutations/jobs, and scheduled job state.
- `fleet logs notes` prints recent build output, server `ctx.log` lines, and uncaught browser errors.

Ask your agent to inspect the current data shape before changing it — a build that compiles can still break old documents stored in `ctx.db`.

## Test server operations from the CLI

Your agent can call queries, mutations, and jobs directly from the terminal on the computer that owns the checkout:

```sh
fleet call notes queries notes
fleet call notes mutations addNote '{"text":"A note from my agent"}'
fleet call notes jobs dailyCheck
```

Mutations and jobs run as you and write to real app data. Back up the database first before testing risky changes.

## Verify changes cleanly

After an edit, your agent should verify two things before reporting `https://<app>.fleet`:

1. Give the rebuild a few seconds, then run `fleet inspect notes` (and `fleet logs notes` if needed) to confirm a new build revision succeeded with no error (remember: a failed build falls back to the previous working bundle, which can look like an edit didn't apply).
2. Exercise changed queries or mutations with `fleet call`.

For changes that touch stored data or visual behavior you want double-checked, ask explicitly for a browser pass or data check.

## Back up before risky edits

Before changing how an app stores data, take a consistent SQLite snapshot:

```sh
fleet backup notes --output notes-before-change.sqlite
```

Keep backups outside the app host when the data matters. Git history and last-good builds protect your source code, not your database. See [data and jobs](/docs/data-and-jobs#back-up-and-restore).

Keep server credentials in `.env.fleet.server` (accessed via `ctx.env`), never in client code or logs. And let Fleet handle auth and serving — don't add a second login screen or start Vite inside a Fleet app.
